# আর্কিটেকচার ডিসিশন রেকর্ড (ADR): প্রোটোকল সিলেকশন সিঙ্ক

**তারিখ:** ১২ আগস্ট, ২০২৬  
**বিষয়:** Fasting Screen-এ প্রোটোকল পরিবর্তনের সময় API কলের অপ্টিমাইজেশন  
**স্ট্যাটাস:** সম্পন্ন (Resolved)

---

## ১. প্রেক্ষাপট (Context)
আমাদের অ্যাপের Fasting Screen-এ ইউজাররা বিভিন্ন ফাস্টিং প্রোটোকল (যেমন 16:8, 18:6) চিপস বা বাটনের মাধ্যমে সিলেক্ট করতে পারেন। ইউজার যেন অ্যাপ থেকে বের হয়ে আবার ঢুকলেও তার সিলেক্ট করা প্রোটোকলটি দেখতে পান, সেজন্য প্রোটোকল পরিবর্তন করার সাথে সাথে ইউজারের "Fasting Preference" ডাটাবেসে সেভ করার প্রয়োজন ছিল।

## ২. আগের অবস্থা ও সমস্যা (Previous State & Problem)
**আগের অবস্থা:** 
আগে ইউজার যখনই কোনো প্রোটোকল চিপে ট্যাপ করতেন, সাথে সাথেই ব্যাকএন্ডে একটি API রিকোয়েস্ট (`PATCH /api/v1/fasting/preference`) পাঠানো হতো। 

**সমস্যা (The Problem):**
- **API Spamming:** ইউজাররা অনেক সময় শুধুমাত্র সময়গুলো (Time Window) কেমন দেখায় তা চেক করার জন্য দ্রুত কয়েকটি প্রোটোকলে (যেমন- 16:8 -> 18:6 -> 20:4) ট্যাপ করেন। প্রতিটি ট্যাপের জন্য একটি করে API কল হওয়ায় সার্ভারে অহেতুক প্রচুর রিকোয়েস্ট যাচ্ছিল।
- **Race Condition & UI Lag:** এত দ্রুত একাধিক API কল হওয়ার কারণে রেসপন্স আসতে দেরি হচ্ছিল এবং UI তে ল্যাগ বা রেস কন্ডিশনের ঝুঁকি তৈরি হয়েছিল।

## ৩. সম্ভাব্য সমাধানসমূহ (Considered Alternatives)
এই সমস্যা সমাধানে আমরা তিনটি উপায়ের কথা ভেবেছিলাম:
1. **Raw Immediate API Sync (আগের উপায়):** সাথে সাথে ডাটা সেভ হয়, কিন্তু সার্ভারে স্প্যামিং হয়।
2. **Debounced Sync:** ইউজার ট্যাপ করা থামানোর পর একটি নির্দিষ্ট সময় (যেমন- ৬০০ মিলি-সেকেন্ড) অপেক্ষা করে তারপর API কল করা। এটি স্প্যামিং কমায় কিন্তু সম্পূর্ণ API কল বন্ধ করে না। 
3. **Local State Only + Start Button Sync (সর্বোত্তম বিকল্প):** প্রোটোকল সিলেকশনের সময় কোনো API কল না করে শুধু লোকাল স্টেট আপডেট করা এবং ইউজার যখন "Start fast" এ ট্যাপ করবেন, তখন API-এর মাধ্যমে ডাটা সেভ করা।

## ৪. আমাদের সমাধান (The Solution)
সার্ভারের ওপর চাপ শূন্যে নামিয়ে আনতে এবং অ্যাপের পারফরম্যান্স সর্বোচ্চ করতে আমরা **Local State Only + Start Button Sync (Alternative Approach)** পদ্ধতিটি গ্রহণ করেছি।

**কিভাবে ইমপ্লিমেন্ট করা হয়েছে:**
- `fasting.tsx` ফাইলের `onSelectProtocol` ফাংশন থেকে Debounce এবং `selectProtocol.mutate()` কলগুলো পুরোপুরি মুছে ফেলা হয়েছে।
- এখন প্রোটোকল সিলেক্ট করলে শুধু অ্যাপের ভেতরের লোকাল স্টেট (`selectedProtocol`) আপডেট হয়।
- যখন ইউজার **"Start fast"** বাটনে ট্যাপ করেন (`onStart` ফাংশন), তখন আমরা চেক করি ইউজারের ডিফল্ট প্রোটোকল পরিবর্তন হয়েছে কিনা। পরিবর্তন হলে আমরা ফাস্ট শুরু করার ঠিক আগে `selectProtocol.mutate(selectedProtocol)` ফায়ার করি এবং ব্যাকএন্ডে সেভ করি।

## ৫. প্রভাব ও ফলাফল (Impact & Results)
- **জিরো সার্ভার লোড:** ইউজার সারাদিন প্রোটোকল পরিবর্তন করে দেখলেও সার্ভারে কোনো রিকোয়েস্ট যাবে না।
- **অত্যন্ত দ্রুত UI (Snappy UI):** কোনো নেটওয়ার্ক কলের জন্য অপেক্ষা করতে হয় না বলে প্রোটোকল সিলেকশন এখন চোখের পলকে (Instant) কাজ করে।
- **ডেটা কনসিস্টেন্সি:** ইউজার যখনই ফাস্ট শুরু করবেন, তার পছন্দসই প্রোটোকলটি পার্মানেন্টলি ডাটাবেসে সেভ হয়ে যাবে। ফলে অন্য ডিভাইসেও তিনি সঠিক ডেটা পাবেন।
- **কোড ক্লিনআপ:** Debounce-এর জন্য ব্যবহৃত `useRef` এবং `setTimeout`-এর জটিল কোডগুলো মুছে ফেলার কারণে কোডবেস এখন অনেক পরিষ্কার এবং মেইনটেইন করা সহজ।
